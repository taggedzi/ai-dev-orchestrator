# Model routing research plan

**Question.** Can task-level model selection maintain acceptance quality while reducing total cost per accepted task?

1. Compare a fixed-model baseline, a simple eligibility and selection policy, and optional adaptive routing. Review [OpenRouter routing](https://openrouter.ai/blog/insights/model-routing/), [NVIDIA Switchyard](https://nvidia-nemo.github.io/Switchyard/routing_algorithms/model_selection/), [Ollama](https://docs.ollama.com/), and [LM Studio](https://lmstudio.ai/docs). For direct APIs and compatible subscription-authenticated agents, review each candidate's official automation and access documentation before selecting candidates for experiments.
2. Build a comparison matrix covering model selection versus provider fallback, tool and reasoning support, actual model and provider identifiers, usage and pricing visibility, allowed data destinations, spending limits, and retry behavior. Define eligibility filters for privacy, required capabilities, and maximum spend before comparing quality.

**Exit evidence.** Draft a repeatable evaluation with representative planning, implementation, and review tasks. Use the same fixtures, acceptance rubric, and attempt limits for each policy. Compare pass rate, total cost per accepted task including review and failures, retries, and human intervention. Report latency separately and label estimated local or subscription costs.

**Later experiment.** Repeat runs to check result variability. Include a denied fallback and an interrupted request with uncertain usage. Set the quality floor and cost ceiling before the first run.

### Proposed routing and accounting contract

These are proposed coordinator behaviors for draft requirements R2, R5, and R6. [Requirements](../docs/requirements.md) · [Architecture](../docs/architecture.md)

1. **Admit one bounded call.** Before each inference call, including review, condensation, and other auxiliary LLM calls, persist task, run, executor conversation, and local call attempt IDs. Store the requested model, endpoint allowlist and order, fallback permission, required capabilities, effective privacy policy, reasoning and output caps, price snapshot, deadlines, and budget reservation. Count the prompt with room for overhead and reserve a conservative upper estimate across approved routes, with full-rate input, possible cache writes, maximum output including reasoning, and any applicable fixed charges. Apply reservations atomically to task/run totals. Block if a compatible route or a defensible budget bound is unavailable. Baseline requests pin one model and endpoint. A later policy can approve same-model fallback across equivalent eligible endpoints.
2. **Record delivery, identity, and spend independently.** Before the agent can act on output, establish that the response is complete, policy-compliant and valid for the expected tool or schema. Persist any generation ID as early as possible. Capture HTTP status, relevant headers such as `Retry-After`, `error.code`, `error.metadata.error_type` and `limit_source` when supplied, completion status, observed model/provider, and attempt metadata. Keep executor response/event IDs, gateway generation ID, gateway request ID, and upstream ID in distinct fields. Store sanitized evidence and timestamps with no prompt, output, or credential content in the accounting record. Use a durable action record for side-effecting tools so a response or run replay cannot repeat an already-applied action.
3. **Settle one charge per generation.** Track reported, estimated, pending, and unknown values explicitly. A gateway-reported zero is evidence. Missing usage, an SDK estimate, or an initial lookup 404 leaves spend unsettled. Use final `usage.cost` as the first reported charge and reconcile against `data.total_cost` by generation ID. Upsert on gateway/account scope plus generation ID so observations across a stream, replay, and lookup count once. Record discrepancies for review. Use account totals for an aggregate cross-check and SDK estimates as diagnostics. Keep uncertainty and committed reservations visible in milestone totals, including failed, interrupted, and review attempts.
4. **Own retries in the coordinator.** Disable executor/client retries and SDK model fallback for the fixture. Allow bounded replay with a new local attempt ID only when evidence shows the previous request was never sent or a typed response establishes a pre-provider transient rejection. Honor `Retry-After` within the approved deadline and attempt budget. A known in-flight-budget 402 with that header is one documented example. Treat 429/503 according to their source and delivery phase. A 503 meaning no eligible route blocks execution. For a 408/524, socket timeout, or dropped response after possible submission, keep the reservation and start reconciliation before any consideration of replay. If a generation ran, settle its charge and check side effects before any new generation decision. Stop on policy or moderation denial, invalid configuration, incompatible capabilities, exhausted budget, unknown spend after an accepted or possibly sent request, or uncertain tool effects. Handle 401/403 and a non-transient 402 as intervention or policy-reset cases. [Error types][errors] · [Limits][limits] · [HTTP retry semantics][http]
5. **Reconcile before resuming.** Record client cancellation or deadline expiry and move a possibly submitted call to pending reconciliation. For a saved generation ID, poll lookup with bounded backoff within a reconciliation deadline. A 404 can be a candidate for delayed publication, with no documented publication deadline. If the record remains unavailable, preserve unknown spend and the reservation. Without an ID, use approved operator access to Logs by key, time and session as a secondary recovery path. Require unambiguous evidence before assigning a row. Keep execution stopped across reconnect/restart while spend or side effects are unresolved. Surface the known subtotal, reserved exposure, and unresolved attempt to the developer. [Generation lookup][generation] · [Logs][logs] · [Activity export][activity]

```json
{

  "messages": [{"role": "user", "content": "Return a short fixture reply."}],
  "stream": false,
  "max_completion_tokens": 256,
  "reasoning": {"effort": "low"},
  "provider": {
    "only": ["fixture-a/approved"],
    "order": ["fixture-a/approved"],
    "allow_fallbacks": false,
    "require_parameters": true,
    "data_collection": "deny",
    "zdr": true,
    "max_price": {"prompt": 1, "completion": 3}
  }
}
```

**Source-confirmed response path.** A successful body supplies a generation `id`, resolved `model`, completed choice, and `usage`. Opt-in metadata can describe the selected endpoint. The coordinator would persist both identities, use the reported charge, and reconcile by generation ID if needed. For streamed variants it would store the first ID, assemble output, and wait for a valid terminal outcome and usage before releasing tool actions under the proposed contract. **Open.** Fixture A checks which exact values OpenHands preserves. [Chat schema][chat] · [Streaming][streaming] · [Usage][usage] · [Generation lookup][generation]

#### 2. Approved provider fallback

**Source-confirmed API path.** For the same explicit model, add a second approved endpoint to both `provider.only` and `provider.order` and set `allow_fallbacks: true`. Suppose A fails with an upstream 429 before any output and B succeeds. OpenRouter can attempt B within the same client request. The model can stay the same while the provider and price change. With opt-in metadata the response can identify attempt 2 and include A's 429 and B's 200. Lookup or dashboard evidence can identify B as the final provider. The coordinator would record one client submission, the observed gateway attempts, and one reported charge for the generation. OpenRouter documents token charges on the successful fallback and specifies zero-completion protection for a zero-token completion with a blank finish reason, or a response ending in an error finish reason. A disconnect provides incomplete evidence of the final reason or token count. Partial output and reasoning-only output may still incur charges, and auxiliary services can be billed separately. A failed client connection supplies no billing conclusion. [Provider routing][provider] · [Errors][errors] · [Router metadata][router-meta] · [Pricing][pricing] · [Insurance][insurance]

**Source-confirmed policy distinction.** Enabling fallbacks with an order list alone can permit providers outside that list. In fixture B, make the allowed endpoints fail and an unlisted C available. Expect an error or terminal error event and zero outbound calls to C. A no-eligible-endpoint example uses 404 in the metadata guide, while the errors guide also documents 503 for unavailable matching providers. Classify by structured cause and delivery phase. **Open.** The fixture must establish what reaches the executor and confirm no client-side fallback on a denial. [Provider routing][provider] · [Router metadata errors][router-meta] · [Errors][errors]

#### 3. Interrupted request

**Source-confirmed API path.** Set `stream: true`. In the first case, a chunk containing `id: "gen-fixture"` arrives, then the connection drops before terminal usage. Persist the ID immediately and query `GET /generation?id=gen-fixture`. The lookup may reveal cost and cancellation metadata. A partial tool call stays unexecuted. If the provider itself sends an SSE error after headers, it can include `id`, `error.metadata.error_type`, and `finish_reason: "error"` even with HTTP 200. Once output reaches the client, the gateway's normal failover stops. Cancelling the socket stops further processing and billing only on supported upstreams. In the second case, the connection drops after send but before any ID. There is no ID for the documented direct lookup. Both cases enter reconciliation and stop additional dispatch under the proposed policy. [Streaming][streaming] · [Errors][errors] · [Generation reference][generation]

**Open.** The reviewed Chat contract supplies no guaranteed pre-response generation ID header, client-ID lookup, inference idempotency key, or reconnect/resume protocol. `session_id` groups conversation traffic and can affect sticky routing. A lookup-row `request_id` or `upstream_id` is distinct from a client attempt ID. The separate Anthropic Messages error format can return a generation ID in its `request_id` field. Capture headers when available, and use Logs or a scoped session and time window to look for a match. An absent or ambiguous record leaves spend unknown. Reposting an ambiguous generation could pay for both submissions. HTTP's retry rules and SSE framing do not confer OpenRouter replay or deduplication guarantees. [Errors][errors] · [Prompt caching][cache] · [Generation reference][generation] · [Logs][logs] · [HTTP semantics][http] · [SSE specification][sse]

**Source-confirmed alternative for recovery.** Broadcast can asynchronously export generation identity and cost to an observability destination and carry an opaque coordinator attempt ID in `trace`. It can omit prompt and completion bodies in Privacy Mode, though fields such as `stop` can still contain caller-supplied text. **Open.** If a policy-approved destination is available, fixture C can test whether traces arrive after disconnect and carry an unambiguous join key. The proposed baseline leaves Broadcast off. [Broadcast][broadcast]

### Recommendation

**Conditional.** OpenRouter is a viable candidate for explicit model access with bounded provider fallback and a per-generation accounting trail. Begin with the single-model, single-endpoint policy. Adoption for autonomous proof-of-concept runs depends on Issue #13 proving that policy survives every executor call, resolved identity and gateway charges can be captured or reconciled, and an ambiguous interruption durably blocks further spend. Obtain hosted evidence for any routing, billing, or cancellation behavior that the selected policy relies on. If ordinary OpenHands events are insufficient, evaluate a policy-enforcing transport that records gateway evidence before normalization and rerun the fixtures. If the chosen boundary cannot enforce these conditions, leave autonomous paid OpenRouter execution disabled. [Issue #13][issue-13]

### Proposed synthetic-repository evaluation

**Fixture.** Use one small synthetic CLI/service repo with a documented contract, isolated worktrees, a seeded test suite and hidden grading cases. Prepare two variants each of five task types. Use a dependency-ordered design plan, a cross-file implementation or bug fix, tests for a seeded edge case, review of clean and vulnerable candidate patches, and a docs or build-configuration change. Include at least one milestone with dependent tasks, integration and post-integration regressions. Reset isolated tasks to the same base revision for each arm. Keep an untouched holdout. [Draft requirements](../docs/requirements.md)

**Paired runs.** First qualify tool calls, schema output and accounting using a scripted endpoint and synthetic inputs under Issues #11 and #13. Later compare fixed selection and deterministic task rules on the same fixtures with the same OpenHands release, tool set, starting evidence, acceptance rubric, retry limits and reviewer. Use the same eligible model pool for rule and adaptive arms and use its capable profile for the fixed baseline. Report differences when a hosted router or separate executor cannot use that pool or harness. Randomize arm order within each task and run three fresh trials per task/arm as a pilot. Record fixture and grader commits, runtime and model versions or digests, prompt and configuration hashes, offered seed where supported, price snapshot and outcome. Pin inputs and retain artifacts so a reviewer can rerun or inspect the trial. A model/provider change requires a new cohort or an explicitly paired rerun. [Issue #11][m104-issue-11] · [Issue #13][issue-13]

**Acceptance.** Grade candidate revisions with hidden checks and an independent, blinded reviewer using the same reviewed revision, acceptance criteria and evidence across arms. Keep the initial reviewer profile fixed and log follow-up review and adjudication effort. For planning, grade dependency order, requirement coverage, alternatives and feasibility. For patches, require regression and scope checks. For generated tests, require proof they detect seeded faults. For review tasks, grade defect severity, detection and false positives. For docs and maintenance, verify examples and clean builds. Freeze the rubric before running. Proposed starting gates are all mandatory checks passing, no confirmed critical defect in any accepted result, at least 90% accepted trials overall and at least 80% in every task type. Review thresholds and the cost ceiling with the developer before the experiment. [Draft requirements](../docs/requirements.md)

**Cost per accepted task.** Divide total cost across every started trial by the number of accepted trials, counting at most one acceptance per task trial. Include failed, cancelled and exhausted attempts, router and judge calls, cache costs, verification compute, independent review, human adjudication and corrective work. Report zero accepted as no finite cost per acceptance. Keep billed API costs, estimated local costs (machine time, energy and an agreed amortization rate), subscription allocation or marginal credits, and valued human time visible as components. Show known subtotal and pending/unknown exposure separately. An unknown bill is never a zero. Add an allocation sensitivity check for local hardware, subscription quota and human effort. [Usage accounting][usage] · [Claude pricing][m104-an-pricing] · [Codex plan rules][m104-codex-plan]

**Variability and repeat failures.** Record first-pass and eventual acceptance, retries, repeated failure classes, reviewer disagreement, false acceptances, human interventions and elapsed time. Propose one authorized retry after diagnosis, bounded by the same per-task exposure across arms. Inject one recoverable failure and one ambiguous or denied operation in dedicated conformance cases, reported separately from ordinary quality trials. Report per-task paired deltas and task-level uncertainty intervals, resampling task variants as groups to keep their repeat trials together. Treat the ten-variant pilot as directional. Expand the held-out sample if uncertainty crosses a decision boundary or one task family drives the apparent gain. [Draft requirements](../docs/requirements.md)

### Recommendation and decision gates

**Accept deterministic task rules for the initial proof of concept, with a fixed-model control.** Keep selection in the coordinator, bind each OpenHands conversation to its approved profile, and start with a small versioned mapping for planning, routine edits, complex debugging and independent review. Select the model and supported effort after filtering policy and capabilities. A task retry may select a stronger eligible profile following a diagnosed quality failure. Use one verified route for the initial executor fixture. OpenRouter with a concrete model and endpoint is the first hosted candidate under M1-03's conditions. Ollama is the first local candidate if an eligible model fits the target host and passes the tool loop. [Draft architecture](../docs/architecture.md) · [M1-03 findings](#m1-03-openrouter-findings)

**Open adoption gate for adaptive routing.** Advance an adaptive trial after deterministic runs show frequent within-task changes in capability needs, costly fixed-tier turns or recurring failures that an earlier switch could plausibly prevent. Compare against deterministic rules with the same eligible pool, then run an ablation that separates task-entry classification from turn-level switching. For adoption, require zero destination or budget-control failures and complete attribution of resolved routes and spend or explicit reconciliation of unknowns.

**Quality.** Require no demonstrated quality regression against deterministic rules on held-out tasks. Preserve the overall and per-task-type quality floors and the critical-defect gate. Before benchmarking, record the quality metrics and how paired results and uncertainty will be judged. Any statistical tolerance requires explicit developer approval before benchmarking. If the evidence is inconclusive, keep adoption open and expand the held-out sample.

**Cost.** Keep at least 15% lower total cost per accepted task as the initial target. Require a paired interval excluding zero savings after charging for judges, retries, verification, independent review and added operations. Include a sensitivity analysis for unresolved spend and maintenance time. Adopt only when the savings cover the extra deployment and maintenance cost at expected volume.
