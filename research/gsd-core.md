# GSD Core research plan

**Question.** Can the coordinator reuse GSD Core planning and durable context while retaining control of execution, verification, and approvals?

1. Pin a release or commit of [Open GSD's GSD Core](https://github.com/open-gsd/gsd-core). Read the upstream [workflow documentation](https://github.com/open-gsd/docs/tree/main/core) and trace discovery, planning, execution, verification, and resumption. Inventory the `.planning/` artifacts, their consumers, and which workflows write them.
2. Look for supported ways to hand an approved plan to an external executor and report the outcome. Record host-agent dependencies, schema stability, automatic commits, approval behavior, and versioning or migration support.

**Exit evidence.** Map sample planning artifacts to the draft requirements. Recommend one of workflow integration, artifact-format reuse, or an independent planning model with reasons and open questions. Identify the authoritative writer for each shared record.

**Later experiment.** Use a fixture plan with two dependent tasks. Test external execution, result recording, and resumption. Check for unexpected Git writes, duplicate state, and dependence on a specific host agent.

## M1-02 findings

**Conditional — reuse GSD Core's planning artifacts through a read-only import.** Use GSD for authoring in a dedicated planning workspace. Import a frozen, developer-approved plan into the coordinator's own versioned task records. The coordinator owns readiness, attempts, execution Git writes, verification, and integration. If the import and recovery checks below fail, use an independent planning model for the proof of concept. [Issue #2][issue] · [Pinned export contract][cli] · [Native recovery gate][execute-resume]

### Pin and evidence

- **Source-confirmed.** OpenGSD `@opengsd/gsd-core` **v1.21.0**, commit `357508df233ccca0dcf4332b385d6bee9b113da9`, MIT. Findings use workflows, agent prompts, docs, and CLI source at that commit. The project research plan's separate upstream docs link now resolves under `core/`. Those guides provide orientation, and the pinned repository is the authority for behavior. [Release][release] · [Commit][pin] · [Package and prerequisites][pkg] · [Upstream workflow guide][guide]
- **Measured.** Local tool discovery found Git and Node on PATH and found no `gsd-tools` command there. No GSD workflow, fixture, or hosted agent was run. The trace below is a source walkthrough. A raw source checkout lacks the compiled CLI modules that ship in the release package. [CLI bootstrap][bootstrap]
- **Assumptions for the walkthrough.** One Git repository, one milestone, one phase, sequential execution on an existing dedicated branch with `git.branching_strategy: none`, planning commits enabled, manual command invocation, and ordinary autonomous tasks. Optional capabilities, TDD, auto-chaining, and external trackers are outside the example.

### Source-confirmed lifecycle and two-task trace

Example milestone **Validate a CLI input**. Phase 1 implements requirement `CLI-01`. Each task has its own plan so the dependency is explicit at the level GSD schedules.

| Plan and task | Dependency and acceptance evidence |
| --- | --- |
| `01-01-PLAN.md`, task 1, add a name validator in `src/validate.js` | `wave: 1`, `depends_on: []`. `node --test test/validate.test.js` checks that a nonempty name passes and a blank or whitespace-only name is rejected. |
| `01-02-PLAN.md`, task 1, use the validator in `src/cli.js` | `wave: 2`, `depends_on: ["01-01"]`. `node --test test/cli.test.js` checks that valid input exits 0 and blank input exits 2 with an error on stderr. |

1. **Discover.** `/gsd:new-project` inspects the checkout, offers codebase mapping for an existing project, and asks follow-up questions. The host writes the project brief and scoped requirements. Optional project researchers and the synthesizer write `research/`. The roadmapper writes the roadmap and initial state and maps requirements to phases. Interactive initialization asks for roadmap approval. Auto initialization accepts a supplied brief and skips that approval gate. For this example, `/gsd:discuss-phase 1` captures blank-name behavior in phase CONTEXT and records the session. [New project][new-project] · [Codebase mapping][map] · [Phase discussion][discuss]
2. **Plan.** `/gsd:plan-phase 1` reads the roadmap and project context through `init.plan-phase`, optionally dispatches a phase researcher, then dispatches the planner. The planner uses PLAN YAML frontmatter for `wave`, `depends_on`, scope and phase-level `must_haves`. Each autonomous task carries XML-like tags for files, action, verification, acceptance criteria, and done conditions. The optional plan checker reviews coverage, dependencies and scope, with a bounded three-iteration revision loop. The workflow updates tracking and can commit the plans and ROADMAP/STATE. Interactive planner confirmation and checker success are workflow signals. The approved revision and approver for this project would be recorded by the coordinator. [Plan workflow][plan] · [Planner][planner] · [PLAN schema][plan-schema]
3. **Execute the first task.** `/gsd:execute-phase 1` uses `phase-plan-index` for dependency waves and readiness. It skips summarized, blocked or not-ready plans and dispatches a host executor for each eligible plan. Initially only `01-01` is ready. The native index checks for predecessor summaries when computing readiness. The executor edits the declared code and tests, runs the task checks, and stages and commits the task's changes with a plan-scoped subject such as `feat(01-01): add name validator`. It writes `01-01-SUMMARY.md` with results and commit references and records progress. Metadata has a separate commit path, with the orchestrator responsible for shared tracking files when executing in linked worktrees. Because the example places one task in each plan, the first plan's summary provides a clear scheduling boundary. [Ready-wave gate][ready] · [Executor][executor] · [Plan execution][execute-plan] · [Plan metadata commit][plan-metadata]
4. **Pause and resume.** Assume task 1 and its summary are already committed and task 2 has yet to start. `/gsd:pause-work` writes `HANDOFF.json` and a phase-local `.continue-here.md`, captures the dirty paths from Git, and requests a handoff-only commit. On a fresh `/gsd:resume-work`, the host reads STATE, checks external jobs, interrupted agents, and handoff files, compares recorded dirty paths with Git, and offers the next action. It updates session continuity and removes the JSON handoff after successful resumption. On re-entry to execute-phase the summary filters out `01-01` and `01-02` is eligible. [Pause][pause] · [Resume][resume] · [Execute discovery][execute-discovery]
5. **Check the interruption window.** If the first task commit exists without `01-01-SUMMARY.md`, execute-phase probes branch-scoped plan commits and stops before redispatch. Its documented choices are manual closeout after inspecting commits, a deliberate re-execution path after dealing with the partial history, or an explicitly approved skip. An unavailable commit probe also stops. In a running wave, a lost terminal response is reconciled using the summary and matching recent commits on the expected branch. A single piece of evidence is insufficient. [Safe resume][execute-resume] · [Wave reconciliation][reconcile]
6. **Verify and advance.** After task 2 and its summary, the shared verification step dispatches the phase verifier, records `01-VERIFICATION.md` and reads its verdict. A pass allows `phase.complete` to update ROADMAP, STATE and requirement traceability. `human_needed` routes to UAT and keeps the phase pending. `gaps_found` can produce gap plans and re-enter execution and verification. UAT records the human results separately. A resume with all summaries present but verification missing can re-enter the verification gates. [Verification step][verify-step] · [Phase completion][execute-complete] · [UAT workflow][uat] · [Execute discovery][execute-discovery]

Paths are relative to `.planning/` unless shown otherwise. The writers below describe native GSD operation. [Upstream planning artifact reference][artifacts] · [Architecture inventory][upstream-architecture]

| `ROADMAP.md` | Roadmapper creates it. Plan workflow writes plan lists and dependency annotations via roadmap helpers. Git and per-plan evidence are consulted separately during execution recovery. |
| `config.json` | New-project and config commands, with workstream resolution where applicable. | Init and workflows read mode, model profiles, workflow switches, parallelism and Git policy. |
| `research/{STACK,FEATURES,ARCHITECTURE,PITFALLS,SUMMARY}.md`; `codebase/`, `onboarding/` | Project researchers and synthesizer. | `NN-PP-PLAN.md` | Planner creates and revises plans in response to checker feedback. Import and gap-planning workflows can write plans too. | Checker, native parser/index, executor, verifier and inspection use objectives, dependency edges, task definitions and evidence requirements. |
| `NN-PP-SUMMARY.md` | Executor or host plan workflow after execution. External async closeout can also write a summary after verification. | Execute index and recovery, verifier, UAT, transition and inspection use it as plan-level completion and outcome evidence. |
| `NN-VERIFICATION.md`, `NN-UAT.md`, optional `REVIEW.md` | Verifier writes the verdict and covered-input fingerprint. Execute-phase can seed human checks, and verify-work records UAT responses. | `HANDOFF.json`, `.continue-here.md`, agent history/current-agent markers | Pause-work writes the handoff pair. Execute-plan records agent sessions and checkpoints. Dedicated commands maintain ancillary records. | Resume reconciles outstanding external jobs. Milestone/progress/audit and the corresponding workflows consume archive and ancillary context. |

The CLI source centralizes planning reads in init, roadmap, phase, verification and the planning snapshot, with separate write commands for state, roadmap and phase completion. `planning-workspace` resolves the planning directory and implements a cooperative lock for selected writers. Host Write/Edit calls and external file editors can still write files directly. A shared mutable `.planning/` directory would require coordination beyond this lock. ### Source-confirmed Git and repository writes

| Trigger | Write behavior |
| --- | --- |
| New project and brownfield discovery | Can run `git init` in a non-repository. Writes `.planning/` and can add `.planning/` to `.gitignore`. Generates the host's repository instruction file, such as `CLAUDE.md` or `AGENTS.md`. Scoped documentation commits cover the brief, config, research, requirements and initial roadmap/state as stages finish. The PROJECT commit call precedes the new config questionnaire. Mapping can commit codebase docs. [Initialization][new-project] · [Mapping][map] |
| Discuss and plan | Discuss requests separate context/log and session-state commits. Planning creates phase directories and PLAN files, may create research/validation artifacts, revises planning metadata, and has a scoped finalize commit for plans, STATE and ROADMAP. The workflow instructs the host to leave branch identity alone during planning, while the shared commit helper can create and switch to a configured new phase/milestone branch when its predicates allow it. [Discuss writes][discuss-write] · [Plan commit][plan-write] · [Branch creation logic][commit-branch] |
| Execute | The executor performs task source/test writes and normally stages selected paths and invokes raw Git for task commits. Multi-repo execution can use `commit-to-subrepo`. Plan metadata and phase closeout can add separate commits. A structural codebase-map refresh can request an amend. Parallel paths can create worktrees/branches, merge, and clean them up. The executor prompts in the pinned workflow explicitly request normal hooks on parallel commits. The configuration docs describe a `--no-verify` pattern, and the helper supports the flag. Confirm actual hook invocation on the target host. [Task commits][task-commit] · [Metadata and map writes][plan-metadata] · [Execute worktrees][execute-worktrees] · [Helper flags][commit-cli] · [Configuration][git-config] |
| Pause, verify, transition and ship | Pause requests a narrow documentation commit. Resume updates continuity and may delete the consumed handoff. Execute and UAT update verification, tracking and gaps; eligible changes can be committed. Optional ship pushes and creates a PR, and milestone completion archives planning records and can tag. These are workflow actions to exclude from an external read-only import. [Pause commit][pause-write] · [Resume][resume] · [UAT][uat] · [Ship][ship] · [Milestone closeout][milestone] |

The commit helper checks per-phase override, effective project policy, Git ignore and default behavior. An intentional skip returns `committed: false` and `skipped: true`. Normal explicit path lists scope staging and the commit. An explicitly named directory can include unrelated changes below it. Amend and merge handling have distinct scoping rules. The helper rejects an out-of-worktree write or non-repository when its context check applies. Disabling planning commits still permits planning file writes and the task executor's Git writes. The optional commit-docs pre-commit guard checks staged planning paths when invoked. Treat host/Git permissions and workspace isolation as the enforcement boundary. ### Source-confirmed interoperability and host boundary

- **Preferred read interface.** `gsd-tools query project-context` reports the resolved checkout and planning root. `gsd-tools query planning inspect` emits `schema_version: 1`, with documented top-level keys and coded diagnostics for missing, partial or conflicting evidence. Unknown schema versions and nonzero CLI exits should fail import. An invalid verification status, for example, makes the query fail. It projects phase goals/dependencies, plans, task names, planned files, acceptance criteria, done conditions and separate verification/UAT/roadmap evidence. The docs call it read-only. Output above roughly 50 KB may use a temporary spill file which the CLI resolves for stdout. The source assembles the snapshot from multiple reads, so use an immutable or quiescent input for import. [Project context][context] · [CLI contract][cli] · [Snapshot fields and output][inspect-output]
- **Scheduling requires validation.** Snapshot plan waves are declared values. `phase-plan-index` computes in-phase dependency waves, rejects cycles and warns when an unresolved edge is dropped from wave calculation. The readiness fields still mark that dependent plan not ready. Use `ready_plans` when comparing native behavior because `runnable` only rules out completed and halt-blocked plans. An external scheduler should validate the complete graph, including phase dependencies, and reject degraded dependencies or ambiguity. Task rows omit runnable actions and verification commands. Preserve the approved raw PLAN file and extract those fields using the pinned grammar or require an explicit coordinator-authored task specification. Task-level status and changed files are limited by summary provenance. A normal plan summary can leave task-level changes and status unknown. There is no attempt ID, approval identity, accepted revision, or cost ledger in the snapshot. [Dependency index][phase-index] · [Plan projection][inspect-plans] · [Task projection][inspect-tasks] · [PLAN schema][plan-schema]
- **Other interfaces.** The bundled stdio MCP companion exposes command invocation and planning file read/write. The import workflow ingests an external plan and uses the plan-checker; it writes plans and can commit. A capability can hand off deferred work with an async-job manifest (version `1.0`) and expected artifacts; resume checks matching jobs first and requires explicit user confirmation before running manifest-supplied commands. The task resolver can provide task content from an external tracker using `tracker-id`; that content can supersede inline action and checks. These surfaces cover commands, files, task content or deferred jobs. The reviewed interfaces do not expose a general completion transaction for an arbitrary external executor with attempts, idempotent replay, revision-bound acceptance and approval. [MCP tools][mcp] · [Import][import] · [Async contract][async] · [Task resolver][task-router] · [Task execution][execute-plan]
- **Version scope.** The npm release and CLI exit contract are versioned. STATE has `gsd_state_version: '1.0'`; HANDOFF has a `version: "1.0"` template; PLAN/SUMMARY/VERIFICATION have documented frontmatter checks. The snapshot and async manifest publish consumer contracts. The versioning policy names config, CLI flags and runtime APIs, and the docs describe installer migrations and a specific `from-gsd2` import. I found no general migration or forward-compatibility guarantee for the Markdown bundle as an external scheduler's storage format. Pin the release and snapshot schema and rerun fixture checks on each upgrade. [Version policy][versioning] · [STATE schema][state-schema] · [Handoff template][handoff] · [Frontmatter checks][frontmatter] · [CLI exit contract][exit] · [Import/migration CLI][commit-cli]
- **Host coupling.** The standalone Node CLI handles local parsing and many deterministic reads/writes and gates. Natural-language interviewing, artifact authoring, task implementation, review, dispatch, approval prompts, context/tool availability and interrupted-agent continuation rely on the host and its model. The installer transforms skills, agent definitions and hooks per host. Claude has native lifecycle hooks and harness worktree support. Codex uses skills and TOML agent definitions, advertises orchestrator-managed worktrees and has a different hook surface. Kimi Code can dispatch built-in roles with the GSD persona carried separately. Host and shell fit, including the Bash-style workflow fragments on Windows, still needs a run. [Runtime installation][runtime] · [Codex capability][codex] · [Claude capability][claude] · [Dispatch mapping][dispatch]

### Proposed authority and fit against the project drafts

| Record | Authoritative writer and relationship to sample artifacts |
| --- | --- |
| Candidate intent and discovery context (R1, R8) | GSD planning host in its planning workspace. It owns candidate PROJECT, REQUIREMENTS, ROADMAP, CONTEXT and PLAN revisions. Export a pinned source revision, paths and hashes. |
| Approved schedule and scope (R1, R7) | Coordinator records the immutable approved import with a developer approval reference and stable task IDs. The sample plan edges and criteria seed this record. Later upstream edits require a new approved revision. |
| Implementation attempts, revisions, status, and model/usage (R2, R3, R5, R6, R9) | Coordinator owns the durable attempt ledger. An assigned executor writes code in its isolated attempt workspace within coordinator policy. Store revision, logs, usage and ambiguity there. STATE/HANDOFF/SUMMARY may inform diagnosis. |
| Verification, review and integration (R4, R7) | Coordinator records revision-bound automated evidence, independent reviewer decisions, integration revisions and regression results. The GSD acceptance criteria and report shapes are inputs. A GSD summary, UAT result or roadmap checkbox alone cannot accept an external revision. |

At the boundary, use a one-way handoff. Leave native GSD progress records under GSD ownership, and record external results in the coordinator's ledger. A later result-export feature would need a defined writer and a tested reconciliation protocol before sharing mutable state. ### Open findings and independent review

| Open finding | Next check and passing evidence |
| --- | --- |
| **O1. Import fidelity and write footprint** | In an isolated fixture, use the pinned published CLI and the two PLAN files above, with stable requirement/phase IDs and explicit `<action>`, `<verify>`, `<acceptance_criteria>`, and `<done>` for both tasks. Run `gsd-tools runtime-identity --raw`, `gsd-tools query project-context`, `gsd-tools query planning inspect`, then `gsd-tools query phase-plan-index 1`. Record tool identity, stdout/stderr, exit status, planning file hashes, Git HEAD, branch, index, refs and working-tree status before and after. Compare repeated imports of the same frozen revision. Require both tasks, the exact edge, usable task checks, and no changes to project files or Git state. Repeat with a missing edge target, a cycle, a malformed plan, and an unsupported snapshot version. Require a refusal to schedule in each degraded case. |
| **O2. Recovery and single-writer ownership** | In the fixture, use a local executor or scripted substitute. Interrupt after task 1's code commit and before writing its outcome record. Preserve the revision and checks, reconcile by task/attempt ID, import the result once, and show task 2 runs only after acceptance. Repeat with ambiguous evidence and confirm that execution pauses for review. In a separate GSD-native fixture, compare resume with the summary present versus missing and capture Git changes, prompts, and whether either task was dispatched twice. |
| **O3. Host and upgrade behavior** | On the selected coding host, verify interactive approval, dispatch, hooks, branch/worktree selection and safe resume with the pinned version against the fixture. Compare actual Git writes with the table, especially hook invocation and doc-commit skip. Validate the import against the next candidate GSD revision before upgrading. Keep native automation outside the proof of concept until its host behavior is measured. |

**Decision gate.** O1 and O2 must pass before the proof of concept depends on GSD artifact import. O3 gates any use of the native workflow in an execution workspace. Source review is sufficient to select the read interface for evaluation. It leaves runtime repeatability, external recovery and host parity open.
