# OpenHands research plan

**Question.** Can OpenHands serve as a replaceable, self-hosted executor for an approved development task?

1. Review the [SDK repository](https://github.com/OpenHands/software-agent-sdk) and [official documentation](https://docs.openhands.dev/). Pin a release or commit and map the supported local and remote execution interfaces. Trace a task from workspace creation and model configuration through status, cancellation, resumption, and cleanup.
2. Fill in a capability matrix with columns for API or source location, observed behavior, unknowns, and later test. Cover sandbox permissions, credential and network controls, events and artifacts, usage and cost, cancellation, restart recovery, host prerequisites, and licensing.

**Exit evidence.** Produce a lifecycle table and a candidate handoff contract for the coordinator. Identify who owns retries and which failures leave an unknown outcome. Record a recommendation to proceed with a later spike, keep investigating, or compare another executor.

**Later experiment.** On a fixture repository, exercise a successful run, cancellation, and interruption during execution. Compare the observed state, workspace changes, and usage before and after resumption.

## M1-01 findings

**Scope.** Reviewed OpenHands Software Agent SDK and Agent Server `v1.62.0` at commit `504a88cab0fb48ee5226238ad7b8f1d865fa84a8` on 2026-11-16. The candidate is an Agent Server running its default local conversation runtime inside a dedicated, self-hosted Linux container. The coordinator connects over REST/WebSocket or via the Python SDK. The embedded SDK is included for comparison. Hosted APIs and the server-managed Docker and hybrid runtimes are outside this review. **Evidence.** **Source-confirmed** describes the pinned code. **Measured** results are unavailable because no Agent Server, model, or upstream tests were run. **Open** items have fixture checks below. The coordinator contract is a proposal based on the source.

### Lifecycle map

REST paths use `C = /api/conversations/{id}`, where `{id}` is the conversation UUID. A conversation holds the agent's working context and can run multiple times. [API routing][api-routes] · [Run route][run-route]

| Provision and launch | Embedded `Conversation(agent=…, workspace=…)` with a local path. Remote `RemoteConversation.create(workspace, request)` or `POST /api/conversations`. | The SDK selects local or remote execution by workspace type. Server creation accepts a server-visible working directory and an agent, agent settings, or saved profile. A supplied `initial_message` is saved and starts a background run. Otherwise, `POST C/events` with `run=false` saves input and `POST C/run` starts it, mirroring SDK `send_message()` then `run()`. Create returns 201 for new and 200 for reuse of a caller-supplied UUID. Reuse skips initial-message delivery, so lookup after a lost create response must also verify prompt delivery. A combined message-and-run response of 429 can mean the message was saved. ### Self-hosting prerequisites and controls

| Area | Source-confirmed behavior and integration risk | Open check |

| Host and persistence | The server package requires Python 3.12+ and exposes an `agent-server` entry point and `/health` and `/ready`. The Linux image supplies Bash, Git, and tmux. SDK-managed Docker requires a reachable Docker daemon, a compatible Linux image and platform, and a free port. Match SDK packages and the future image to the pinned release and record the deployed image digest. Persist the checkout and the server's `OH_CONVERSATIONS_PATH` on writable paths that survive server replacement. Each conversation has a UUID-named directory containing `meta.json`, `base_state.json`, and the event history. ### What interruption leaves ambiguous

- **Source-confirmed, client loss.** WebSocket disconnect unsubscribes the listener. The run is a separate server task. A timeout or lost response can occur after creation, message delivery, or a run trigger has taken effect. A stable conversation UUID helps reconcile creation while the catalog survives. The mapped message and run routes offer no per-message or per-run idempotency key. [Disconnect][socket-disconnect] · [Launch order][launch-service] · [Reuse][create-reuse] · [Message route][message-route] · [Run route][run-route]
- **Source-confirmed, server loss.** On startup the service hydrates persisted running records where it can take ownership. A stale `running` becomes `error` and recovery can add a synthetic error for the first unmatched tool action. The run awaits a new trigger. The event file and saved conversation head can differ at the crash boundary. Terminal sessions may be reclaimed at server startup. [Catalog recovery][cold-start] · [Interrupted tool recovery][event-recovery] · [Terminal startup cleanup][restart-tmux]
- **Integration inference.** A missing observation or synthetic error leaves actual effects unknown. A command may already have written files or triggered an external action. A model provider may have processed or charged for a request before the response and usage reached durable state. Reconcile history with the checkout, observable effects, and usage records before resuming or retrying. Retain an unknown outcome when evidence is missing. [Interrupted tool recovery][event-recovery] · [Response accounting][response-metrics]

### Candidate coordinator handoff

The coordinator owns the proposed task and attempt IDs and stores their mapping to the OpenHands conversation UUID. The UUID identifies the native OpenHands conversation. Attempt identity and task-level retry guarantees depend on the coordinator's records and reconciliation. [Conversation request][start-request] · [Run route][run-route]

- **Input and identity.** Persist coordinator task and attempt IDs, chosen OpenHands conversation UUID, server and container identity, isolated workspace and base SHA, approved prompt, model/profile and credential references, and limits before sending work. Keep provider configuration behind the executor interface. The runtime needs a reachable approved model endpoint and credentials if that endpoint requires them.
- **Observation and receipt.** Retain the last observed event IDs, raw status, final response, artifact locations and checksums, and usage snapshots with timestamps and availability. Deduplicate events by ID and backfill history after reconnect. Preserve the checkout until the patch and test evidence are captured for independent verification.
- **Retry ownership.** OpenHands owns configured transient LLM retries. The coordinator owns task retry and resume decisions. Reconcile by UUID and verify prompt delivery before any resend. Resume the same conversation only after checking state, workspace, and credentials. A run trigger can implicitly approve pending actions. When status is `waiting_for_confirmation`, require the developer's decision and use `POST C/events/respond_to_confirmation`. A new attempt gets a new UUID and fresh checkout. [Implicit confirmation][implicit-confirm] · [Confirmation route][confirm-route] · [LLM retry policy][llm-retry] · [Attach][attach] · [Run conflicts][run-route]
- **Cancellation safety boundary.** Record the interrupt acknowledgement as a pending cancellation. Mark the attempt cancelled only after verifying that the run and its tools have stopped or that the dedicated sandbox is stopped. Hold workspace reuse and task retries while execution could still be active. Preserve available evidence and escalate if execution state or side effects remain unknown. [Stop routes][stop-routes] · [Stop drain][stop-drain]

### Recommendation

**Conditional.** Advance OpenHands v1.62.0 to a no-credit executor spike. The pinned interfaces cover launch, observation, artifact capture, usage, stop, reattach, and cleanup. Adoption for the proof of concept depends on demonstrating that the coordinator can safely recover or record an unknown outcome after interruption, capture reviewable artifacts and distinguish missing usage, and stop and reclaim the isolated runtime. Run checks A–E on the pinned deployment under Issue #11 before selecting OpenHands as the production executor. [Runtime fixture issue][issue-fixture]
