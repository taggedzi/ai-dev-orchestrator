## One-variable diagnostic prepared for review

Retain two CPUs, RAM, firmware, graphics, kernel, disks and disconnected networking. Change only the new VM's CPU x2APIC feature from on to off for one bounded boot. Do not change host Hyper-V, WSL, Windows security, kernel arguments, the installed filesystem or tools. Do not pause/resume to rescue the trial. Record the full receipt and drain the serial channel during the existing 60-second ACPI shutdown wait. Preserve the original ten-minute authority bound, 360-second login wait and emergency-stop path.

This hypothesis comes from [VirtualBox issue #861](https://github.com/VirtualBox/virtualbox/issues/861), whose reporter describes a Linux-host lost-IPI case and a combined kernel workaround. That environment differs from this NEM host; disabling x2APIC alone is a controlled probe, not a known fix. [Issue #799](https://github.com/VirtualBox/virtualbox/issues/799) separately describes Windows-host NEM stalls. Neither report proves this machine's cause.

The explicit `--disable-x2apic-diagnostic` option requires reconciliation index 4 from the prior protocol retry, its matching audit tail, post-trial stopped hash and this offline inspection's evidence digest. A fifth continuation is rejected. The next checkpoint does not approve an executor experiment or general retry policy. Restore x2APIC and disable UART only after confirmed poweroff; if shutdown fails, retain the stop evidence and restore the stopped profile separately. Do not treat a failed cloud-init predicate as a successful overall result.

The initial native attempt, `x2apic-01`, never booted: changing x2APIC also disabled ordinary APIC, and VirtualBox refused the 64-bit guest. Its native state and host log confirm poweroff and process exit; a subsequent explicit restoration confirmed both APIC settings on and UART off. [The platform setter](https://raw.githubusercontent.com/VirtualBox/virtualbox/main/src/VBox/Main/src-server/PlatformX86Impl.cpp), source ID revision `113333` (March 11, 2026), assigns both flags when x2APIC changes. The corrected command re-enables ordinary APIC last. A new pre-start guard requires ordinary APIC, I/O APIC and the firmware level to remain unchanged; tests reject the observed accidental profile. A failed start is now propagated before waiting for a nonexistent serial pipe. One separately approved corrected start may use the unchanged stopped-disk checkpoint; this is not a successful boot observation or an automatic restart.

## Corrected trial result and next check

The separately approved `x2apic-02` trial completed an unattended two-CPU boot and ACPI shutdown, with zero pause/resume interventions or emergency-stop intents. Total preparation time was 234.271 seconds including the stopped-disk hash. The serial capture ends with the kernel's `reboot: Power down`, and the host termination log records VBoxHeadless exiting. The [diagnostic evidence](boot-diagnostic-evidence.json) binds the token-matched receipt, operation/audit records, source snapshot and final native configuration. Ordinary APIC remained enabled; x2APIC was off during this trial and restored on afterward. UART is off, all NICs are disabled, and the VM is stopped.

The unchanged v1 readiness predicate still returns false for cloud-init `disabled`, so the command exited with a hold and retained a failed overall verdict. Its other nine predicates pass. The new marker observation matches the exact installer-proven 132-byte file, and cloud-final is inactive with result success. The disconnected image still reports a failed network-online wait; image hardening must address that explicitly. Do not rewrite the historical v1 results as passes.

This is one promising cycle, not proof of repeatability or of an x2APIC root cause. The next stage should freeze a prospective v2 readiness policy that recognizes only the inspected installer marker, exit-zero/no-error cloud-init state and explicit cloud-final completion/skipping state. Bind the policy to the inspection evidence and test negative controls before applying it. Then require three consecutive cold boot/ACPI shutdown cycles on the same two-CPU x2APIC-off candidate profile, with a new stopped-disk hash at each boundary, no rescue intervention and a hold at the first failure. These are preparation qualification cases, not retries of an executor operation. Keep each boot within its ten-minute authority and 60-second shutdown bounds; approve the frozen three-cycle plan before starting it.
